# FileCrypt v2 开发范围

状态：设计草案，2026-10-14。本文记录准备实施的 v2 范围，不表示已有 v2 读写器或可发布文件格式。精确编码、密码套件参数和资源上限仍须完成规范、向量与审查后冻结。

程序发布版本与文件格式版本分别管理。现有 v1.1.0 发布仍使用文件格式 v1；本目录中的 v2 指 `.fcry` 文件格式版本 2。

## 1. 选择方案 B

v2 保持一个 `.fcry` 文件的使用方式，采用独立格式、分块认证、独立压缩帧和加密元数据。目标是让大文件处理具有明确的认证与资源边界，减少为了完成整体认证而暂存完整解密载荷的需要。

随机数据密钥与用户密码分开管理。首版仍只提供一个密码入口，保留已有的完整换密语义。恢复和换密产生的最终输出，必须在整个文件验证成功后提交；分块认证不改变这一要求。

方案 A 继续作为 v1 维护路线；方案 C 的对象仓库、快照与增量备份不进入本次开发。v2 不继承 v1 的头部、目录编码或整体压缩组织；历史兼容由独立 v1 流程承担。

## 2. 首版范围

| 范围 | 确定的行为 | 尚需落实的部分 |
| --- | --- | --- |
| 交付方式 | 文件或目录加密为一个 `.fcry` 文件，固定布局、小端整数、明确长度；完整顺序恢复 | 精确字段表与编号 |
| 数据组织 | 小文件合包，暂按 4 MiB 内容目标，整文件加入后允许越过目标；大文件单独分块 | 合包映射编码、独立硬限制与大文件块大小 |
| 数据认证 | 有序记录逐块认证，认证结束记录约束全文件完整性 | 编码、认证上下文、序号与用量限制 |
| 压缩 | 沿用 v1 的默认不压缩、`compress` / `-z` 与 `no-compress`，等级暂保持 3；每包或块独立压缩，无收益时回退未压缩数据 | 编码值、长度计数及硬限制；资源测量暂缓 |
| 元数据 | 专用二进制清单置于数据之前，父条目在前、序号为 ID；加密保存原始名称、类型、目录树与映射 | 清单分片的精确编码、大小限制及显示规则 |
| 密钥 | 随机 32 字节数据密钥，Argon2id 与 HKDF-SHA256 派生包装密钥，单密码入口；独立派生各用途密钥，完整头使用 HMAC-SHA256 | 派生上下文、域标签和精确认证字节 |
| 数据算法 | 保留 AES-256-GCM 与 XChaCha20-Poly1305，默认 AES-256-GCM | v2 独立编号、nonce 分配及每密钥使用上限 |
| `info` | 未解锁时只展示公共信息，不宣称文件已认证 | v1/v2 输出差异和受保护字段的提示方式 |
| `encrypt` / `decrypt` | 文件和目录、压缩开关、资源限制、无覆盖默认与失败清理 | 接入 v2 流程，保持平台事务和路径检查 |
| `verify` | 读取全部记录，校验认证、压缩、清单与载荷对应关系，不生成恢复文件 | 分块读取与结束状态机 |
| `rekey` / `-r` | 旧密码、新密码、再次确认；另存或显式替换；生成新数据密钥并完整重加密 | 源版本分发和 v2 内存流水线 |
| 解锁后内容列表 | `list` 与 `-l` 完全等价，共用参数、密码输入、输出和错误行为；完成清单认证与结构校验后显示名称、大小和目录树 | 显示格式与终端转义规则 |
| 进度与安全取消 | 终端自动向 stderr 显示阶段进度，重定向时不刷新动态行；Ctrl+C 请求取消，清理尚未提交的输出 | 关闭进度的选项拼写、平台取消处理与提交时序测试 |

现有密码生成能力继续保留，与文件格式升级无关。表中能力属于首版目标，不能把现有 v1 对应功能视为 v2 已经实现。

### 已确认的使用策略

2026-10-14 确认保留显式新建 v1/v2 的入口，稳定发布后默认创建 v2。所有命令的完整名称与缩写只作为别名，不赋予不同语义；`list` / `-l` 与既有 `rekey` / `-r` 均遵守这一规则。

恢复继续要求显式提供输出路径。v2 首版按指定路径恢复，不用清单中的原始名称替换目标或自动追加后缀；原始名称用于内容列表，用户可以据此自行指定恢复名。目录输出仍是恢复后的根目录；v1 继续保持原有扩展名恢复规则。首版不另加省略输出路径或自动按原名恢复的模式。

压缩的默认值、开关和等级暂时沿用 v1；这一决定不撤销 v2 已确定的分块认证和独立帧设计。容量目标、KDF 成本与资源参数评估继续暂缓，不在本轮测量或调整已有默认值。后续实现仍须执行有界解析和算法使用限制，不能把评估暂缓理解为取消检查。

### 已确认的技术方向

2026-10-14 确认以下技术选择，其中小文件由原建议的单独记录改为合包。确认的是设计方向，精确字节规范、测试向量与审查仍未完成。

| 项目 | 采用的方向 |
| --- | --- |
| 编码与扩展 | 固定布局、小端整数、明确长度；首版不设通用可跳过扩展区，拒绝未知类型、标志及非零保留字段 |
| 完整清单 | 专用二进制，父条目在前、条目序号作为 ID；在数据之前按片段完整认证并核对总长度和条目数 |
| 小文件合包 | 暂将 4 MB 按 4 MiB（4,194,304 字节）解释为压缩前文件内容的软目标；小文件整份加入，达到或超过目标即结束该包 |
| 压缩与回退 | 每个包或大文件块的数据区压缩为恰好一个独立 Zstd 帧；结果不更小时保存未压缩数据；清单与映射不压缩 |
| 密钥组合 | 32 字节 DEK、Argon2id、HKDF-SHA256 用途分离；完整头使用 32 字节 HMAC-SHA256 标签，包装 AEAD 跟随数据套件，AEAD 标签为 16 字节 |
| nonce 与结束 | 记录 nonce 按递增序号构造，各用途使用独立密钥；逐记录认证、严格顺序、完整映射、认证 END 及精确 EOF 共同约束完整性，不另加全文件摘要 |

合包暂以小于 4 MiB 的非空文件为对象；加入前未满、加入后封包，因此包内容可能大于 4 MiB，但严格小于 8 MiB。空文件只记清单，达到或超过 4 MiB 的文件单独分块。映射与整个记录另受硬限制，必要时提前封包；不足目标的尾包同样有效。具体规则见[文件格式中的合包约定](FILE_FORMAT.md#小文件合包与大文件分块)。

### 内容列表与完整验证

内容列表可以只读取并认证完整清单，不必读取全部数据。成功只表示清单已通过认证和结构校验；不能表示数据记录、结束记录或整个文件没有损坏。输出必须明确这一区别，并指向 `verify` 进行完整验证。

清单中的路径在显示前也需要结构校验和终端安全转义，不能让控制字符伪装成程序状态。实际恢复另行执行目标文件系统的名称及冲突检查；格式有效的名称不保证可在每个平台创建。

### 进度与取消

连接终端时自动向 stderr 显示进度，重定向时不刷新动态行，并提供关闭进度的选项；Ctrl+C 请求安全取消。进度按读取、KDF、加密或解密、校验、提交等实际阶段显示。能够测量的阶段报告已处理字节及对应总量；没有可靠总量时报告阶段或已处理量，不编造精确百分比。读取密文、解压输出和逻辑文件字节不是同一计量口径。

KDF 运行期间不假定底层库支持即时中断，也不显示虚假的精确进度；取消请求最迟在下一个安全检查点处理。普通取消不能承诺在强制结束进程或系统崩溃后仍完成清理。

提交前取消应丢弃本次临时输出并保留原文件。最终提交是明确的状态边界：原子替换已成功后，不能把后来到达的取消请求报告为“已撤销”或删除已经提交的文件。提交后持久化确认失败也必须说明真实状态。

### 换密语义

`rekey` 与 `-r` 保持等价，密码继续通过交互输入，不接收明文密码命令行参数。默认另存要求目标不存在，只有显式 `--replace` 才替换输入文件。

v2 换密生成新的数据密钥和容器身份，完整验证源内容并完成新文件校验后提交，解密载荷不主动暂存为普通文件。旧文件、历史备份仍可使用旧密码打开；换密不能让已经复制出去的内容失效。

只重包同一个数据密钥不会撤销持有旧密码及旧包装信息者的访问，因此不以“快速优化”的方式替换 `rekey`。首版不提供只重包模式。

## 3. v1 兼容与默认版本

各格式只共用 `FCRY + Little-Endian uint16 Version` 六字节前缀。新版程序根据版本进入独立的完整流程：

```text
共用识别前缀
    ├─ Version = 1 → v1 格式、密钥、认证与载荷流程
    ├─ Version = 2 → v2 格式、密钥、认证与载荷流程
    └─ 未知版本    → 明确拒绝
```

- v1 的 `info`、解密、验证和换密继续可用；v1 `rekey` 输出仍为 v1，不暗中迁移。
- v1 与 v2 解析或认证失败后都不得尝试另一版本；版本字段用于路由，仍需纳入各版本的认证绑定。
- v1 历史文件继续执行原有协议规则和运行资源检查；兼容不要求保留实现缺陷或取消限制。
- v2 未达到发布门槛前，新建文件默认仍为 v1；稳定发布时再切换默认 v2，并同步帮助和发布说明。
- 开发期和稳定发布后均保留显式选择创建 v1/v2 的入口，格式选项的拼写另随 CLI 细节确定。选择 v1 时拒绝不能表达的 v2 专有选项，不静默丢弃；读取旧文件和 v1 换密不依赖新建格式的选择。
- 旧程序明确拒绝 v2 属于预期行为，不要求旧程序解析 v2。

历史规范见 [v1 文件格式](../v1/FILE_FORMAT.md)和[v1 协议边界](../v1/PROTOCOL_BOUNDARIES_V1.md)。跨版本的模块职责与错误约定继续由[架构](../ARCHITECTURE.md)和[错误语义](../ERROR_HANDLING.md)说明。

## 4. 首版不做的功能

| 功能 | 暂缓原因与后续条件 |
| --- | --- |
| 只重包数据密钥、多密码入口、独立恢复码 | 增加密钥生命周期、撤销与用户提示问题；先完成单密码和完整换密 |
| 公钥收件人、RSA、签名 | 需要明确分享或无人值守备份场景，以及密钥保存、导入、指纹核对和恢复流程 |
| 随机提取、选择恢复 | 首版先完成整个文件或目录的恢复；后续选择恢复可完整顺序验证后只写选中内容，随机访问则另需经过认证的定位信息 |
| 换密时显式升级 KDF 参数 | 测量后再设计参数更新选项，首版不隐式修改旧文件的 KDF 策略 |
| 快照、增量备份、去重、并发仓库 | 属于方案 C 的存储系统工作，超出单文件容器范围 |
| 追加、原地改写、断点续写 | 涉及 nonce、密钥用量、崩溃状态与恢复协议，首版每次重新创建容器 |
| 专用格式迁移与降级导出 | 不是读取 v1 的必要条件，暂不增加新命令或自动转换 |

公钥能力后续优先评估基于 X25519 的标准封装，例如 HPKE；只有需要复用 RSA 密钥、证书或硬件时，再评估 RSA-OAEP。这里保留需求方向，不预留已承诺的套件编号、收件人字段或兼容空位。公钥加密、作者签名和忘记密码后的恢复是不同需求，不能由一个“支持 RSA”选项代替。

## 5. 文档与实施顺序

本目录以[文件格式草案](FILE_FORMAT.md)、[密码学草案](CRYPTOGRAPHY.md)和[验收方案](VALIDATION.md)分别记录编码、密码组合与验证要求。当前不存在冻结的完整字节级规范，也没有已完成的 v2 向量结果。

| 阶段 | 产出 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1. 规范与历史基线 | 明确首版范围；冻结可审查的编码、认证、nonce 和限制；固定历史 v1 样本与 v2 预期向量 | 未决协议事项有结论，向量可独立复核，v1 基线可重复执行 |
| 2. 未压缩单文件 | v2 编解码与 `info`、加密、解密、验证、完整换密闭环 | 截断、错序、篡改、结束检查、资源边界和失败清理通过 |
| 3. 压缩、目录与使用流程 | 独立帧及未压缩回退、小文件合包、完整清单、所有首版命令、内容列表、进度及取消 | 合包与目录映射、跨平台恢复通过，资源与压缩测量完成 |
| 4. 发布准备 | 协议与安全审查、固定互操作向量、Windows/Linux 回归、发布文档 | 满足验收方案后冻结可发布格式，决定默认写入版本切换 |

规范进入实现前冻结实现所需的规则；若试验发现问题，应显式修订草案、向量和实现，不保持未经发布的实验文件兼容承诺。可发布格式的最终冻结以完整验收和审查为准。

当前 v1.1.0 对应提交 `f073b29` 的 Windows/Linux 验证已通过；这不代表 v2 或后续缓存改动已经验证。Linux 缓存策略的远端复验及资源评估继续记录在 [TODO](../TODO.md)，与 v2 开发分别推进。
