# v2 密码学设计草案

状态：设计草案，2026-10-14。本文记录方案 B 的密码学边界与待冻结事项，不是已经实现或可用于互操作的协议。精确编码、套件编号、密钥派生标签、nonce 构造和使用上限须与测试向量一起审查后冻结。

v2 保持单个 `.fcry` 文件的使用方式，采用随机数据密钥、单密码包装、独立记录认证和加密元数据。v1 继续按[原密码学规范](../v1/CRYPTOGRAPHY.md)处理，不继承本文的新规则。

## 1. 首版决定与未决项

| 项目 | 首版决定 | 仍需冻结 |
| --- | --- | --- |
| 密码入口 | 一个密码，通过 Argon2id 与 HKDF-SHA256 派生包装密钥 | 默认参数、允许范围、派生上下文与运行限制 |
| 数据密钥 | 每个新容器生成独立随机的 32 字节 DEK | 随机容器标识及其长度 |
| 数据与包装算法 | AES-256-GCM 与 XChaCha20-Poly1305 两套完整套件，默认 AES；包装 AEAD 跟随数据套件，AEAD 标签均为 16 字节 | 套件编号、包装字段与 AAD 的精确编码 |
| 完整头认证 | HMAC-SHA256，保留完整的 32 字节标签 | 原始字节覆盖范围、头认证密钥派生与标签位置 |
| 用途分离 | HKDF-SHA256 分别派生包装、头认证、清单、数据与 END 所需密钥 | salt、info 编码、域标签与派生顺序 |
| 数据认证 | 每条记录独立 AEAD；全局顺序、清单映射与 END 约束整体完整性，首版不另加全文件 SHA-256 | 记录编码、AAD、递增序号的 nonce 构造与每套件使用预算 |
| 换密 | 完整轮换 DEK 并重加密，保持源格式版本 | 实现接口与验证向量 |
| 后续能力 | 公钥收件人、恢复密钥、签名另行评估 | 不预先分配线格式编号或承诺兼容扩展 |

两套完整套件表示每个编号确定全部密码学构造，不允许用户任意组合数据算法、包装算法、头认证算法及派生函数。读取器只接受实现和规范共同支持的套件；缺少算法能力时明确拒绝，不能静默换用另一套算法。使用已有 Botan 原语不等于新组合已经得到验证。

## 2. 密码字节与 KDF

密码使用用户输入的 UTF-8 字节；不去除首尾空白、不改变大小写、不做 Unicode 规范化。交互输入的行结束符属于输入分隔，不属于密码。新密码确认按实际字节比较；外观相同但字节不同的 Unicode 字符串仍是不同密码。首版不接受空密码，也不将密码作为命令行参数。

每次创建容器或完整换密都使用密码学安全随机数生成新的 salt。Argon2id 的输入包含密码字节、salt 和文件内明确编码的参数，其输出再经 HKDF-SHA256 派生包装密钥 KEK，不能直接复用为数据记录密钥。Argon2id salt 与 HKDF salt 的作用、长度和具体编码分别定义，不能仅因名称相同就视为同一字段。

Argon2id 的内存、迭代次数和并行度需要在目标设备上测量，分别定义新建默认值、协议合法范围和读者可配置的运行预算。不能将 v1 默认参数直接视为 v2 的已定结论，也不能把某一设备的耗时写成跨平台保证。[RFC 9106 参数选择](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)

解锁前必须先检查头部大小、KDF 编号、整数范围、参数关系和运行预算，再调用 KDF。攻击者可以修改尚未认证的参数，不能为了认证头部而无条件执行其中要求的大量计算。超预算与格式非法分别处理；密码错误或包装认证失败不输出派生密钥及密码内容。

## 3. 密钥层次与用途分离

```text
用户密码 + 新 salt + Argon2id 参数
                 │
                 ▼
           Argon2id 输出
                 │
           HKDF-SHA256
                 │
                 ▼
             包装密钥 KEK ──认证包装──► 随机 32 字节 DEK
                                             │
                         版本 / 套件 / 容器身份 / 用途上下文
                                             │
                                       HKDF-SHA256
                                             │
                                             ▼
                           头认证 / 清单 / 数据 / END 密钥
```

DEK 是独立于密码的 256 位随机密钥材料。包装密钥来自 Argon2id 输出；头认证、清单、数据和 END 密钥来自 DEK，分别通过 HKDF-SHA256 派生，不能把一个输出跨用途直接复用。派生时绑定版本、套件、容器身份与用途，避免不同容器、不同版本或不同记录角色共用同一密钥域。HKDF 的 `info` 承担这种上下文分离，不能替代处理人类密码的 Argon2id。[RFC 5869 上下文绑定](https://www.rfc-editor.org/rfc/rfc5869.html#section-3.2)、[HKDF 与密码的边界](https://www.rfc-editor.org/rfc/rfc5869.html#section-4)

AES 套件以 AES-256-GCM 包装 DEK，XChaCha 套件以 XChaCha20-Poly1305 包装 DEK；两者的包装与记录认证标签均保留完整的 16 字节，不提供标签截短选项。包装和数据使用各自的密钥与 nonce 分配规则，不能因为采用相同 AEAD 就混用状态。

用途名称在本文中是概念，不是可以直接写入实现的域标签。冻结时必须给出完整字节串、长度编码、整数端序、派生顺序和各输出长度。不同字段拼接必须唯一可解析，不能依靠缺少边界的字符串连接或平台本机结构体布局。

密码、KEK、DEK、派生密钥以及认证前的解密缓冲使用适合清理的内存容器，减少不必要副本，不写入日志。该要求不承诺能够抵御操作系统交换、崩溃转储或已控制当前用户进程的攻击者。

## 4. 不变描述与密码包装的认证

协议区分两类头部信息：

| 部分 | 语义 | 认证要求 |
| --- | --- | --- |
| 不变数据描述 | 包含版本、套件、容器身份及解释数据记录所需的固定上下文 | 包装、头认证及各类记录都绑定同一份描述 |
| 密码包装区 | 包含密码入口类型、KDF 参数、salt、包装 nonce、DEK 密文和标签 | 包装认证绑定其控制字段与不变描述；完整头认证覆盖包装区及其他头部字段 |

首版虽然不支持只更新包装区，也要把两种职责分清。这里的“可变包装”是模型边界，不代表允许未认证改写、增加密码槽或原地更新文件头。

解锁顺序为：有界解析公共字段，执行受限 KDF，验证包装并恢复 DEK，派生头认证密钥并验证完整头，然后才允许使用受保护的头部语义和读取清单。仅成功解包 DEK 不能替代完整头部认证。

完整头认证采用 HMAC-SHA256，保留完整的 32 字节标签，不另分配头认证 nonce。认证对象是完整头的原始编码字节，排除该 MAC 标签自身，包含不变描述、密码包装控制字段、DEK 密文及其 AEAD 标签；精确覆盖区间与标签位置仍须在字段表中固定。

依赖关系必须单向：密钥派生上下文与包装 AAD 不得依赖完整头 MAC；包装 AAD 不包含它所认证的 DEK 密文及包装标签。来自 DEK 的用途密钥绑定不变描述和用途，不以包装密文、包装标签或完整头 MAC 作为派生前提。先派生 KEK 并生成包装，再由 DEK 派生头认证密钥，最后认证完整头，避免互相要求对方先产生的循环依赖。

各已定义套件采用固定布局、明确长度与小端整数编码；首版不引入可跳过的通用扩展区。未知类型、未知标志、非零保留字段与非规范编码明确拒绝，不能静默丢弃后只认证重新序列化的结果。是否使用不变描述摘要及其精确编码仍须冻结，不能由调用方自由选择。

数据记录绑定不变描述，而不是把整个可更新密码包装区直接作为各记录的 AAD。头认证负责绑定完整包装状态，逐记录认证负责绑定记录及其所属容器；这两种检查都不能省略。

## 5. 记录认证与整体结束条件

每条记录作为独立 AEAD 消息。认证上下文至少覆盖不变描述、容器身份、记录类型、全局序号及影响记录解释的长度；清单和文件数据的对应关系也必须受认证并由状态机校验。加密清单中的文件标识、逻辑偏移等信息不必全部公开在 AAD 中，但不能成为未认证的路由依据。

数据记录允许容纳多个小文件。包内文件映射同样必须认证，并与清单逐项核对；不能假设一条数据记录只属于一个文件。读取器须检查各文件范围、顺序和逻辑长度，拒绝重叠、遗漏、重复、越界或未声明的数据。

读取器必须按照预期序号和允许的类型转移逐条处理。单条记录认证有效，也不能接受重复、错序、跨容器拼接、未声明数据或超出清单的文件内容。序号计数和长度累计在加法、乘法及类型转换之前检查溢出。

一条记录的明文在该条 AEAD 最终标签通过前只存在于有界内部缓冲中，不交给解压器、目录解析器或用户输出。Botan 的增量解密可能在 `finish` 校验标签前产生明文；这些字节不能提前作为可信内容使用。[Botan AEAD 接口](https://botan.randombit.net/handbook/api_ref/cipher_modes.html#aead-mode)

END 使用通过 HKDF-SHA256 独立派生的用途密钥，认证完整容器的计数与长度关系，至少包括：

- 实际记录计数以及清单和数据记录的对应关系。
- 编码后数据总量与解压后逻辑总量，两者分别计数。
- 各文件的逻辑长度、顺序以及清单声明均已满足。
- END 是唯一结束记录，其后必须恰好到 EOF。

计数是否包含清单、头部、标签和 END 自身，必须在文件格式中逐项定义，不能使用含糊的“总长度”。空文件和空目录仍需完整头、清单及 END。缺少 END、END 后追加字节、计数不符或读取错误均为失败，不能当作正常 EOF。

首版不另加全文件 SHA-256。整体完整性依赖逐条 AEAD、严格序号、完整清单映射、END 的计数与长度以及精确 EOF 同时成立；任何一项缺失，都不能以其他认证成功代替。这是待独立审查和负向向量验证的组合设计决定，不表示只增加一个 END 就已证明容器安全。

清单认证通过只允许报告“清单已认证”；列表功能不能据此宣称整个文件已验证。`verify` 需要遍历全部记录，检查压缩、路径、结构、映射及 END。解密恢复和换密在整体校验完成之前不得提交最终结果。

## 6. nonce 与算法使用预算

两个数据算法都要求同一密钥下的加密调用不重复使用 nonce。不能只依赖记录序号字段足够宽，也不能把每块独立认证理解为容器可以无限大。[RFC 5116 nonce 要求](https://www.rfc-editor.org/rfc/rfc5116.html#section-3.1)

记录 nonce 采用基于递增序号的明确构造，按套件分别定义，不为每块独立随机分配 nonce。是否使用容器相关前缀、各用途如何映射全局序号、END 如何分配 nonce，都须在冻结前给出精确字节规则，并覆盖计数上限附近的向量。包装 nonce 单独定义，不能直接套用数据记录规则。

| 预算 | 必须说明的内容 |
| --- | --- |
| 单消息长度 | 每条记录的明文、AAD 与密文上限，另行限制包装消息与头 MAC 输入长度 |
| 每密钥调用次数 | 各用途的最大加密调用数及对应计数器范围 |
| 每密钥累计用量 | 总字节数或块数，按算法要求计算安全裕量 |
| nonce 唯一性 | 具体构造、端序、溢出拒绝以及每个用途的分配规则 |
| 验证预算 | 畸形记录、失败认证和总资源消耗的运行限制 |

AES-GCM 的单消息约束和整体使用条件需结合其规范计算；v1 单条消息的上限不能直接当作 v2 每个容器的上限，也不能乘以一个任意块数来宣布新的安全容量。[NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)

XChaCha20-Poly1305 的较长 nonce 不取消每消息计数器和每密钥使用约束。两套预算应各自给出依据，并取密码学限制、库实现限制和产品资源限制的共同范围。本草案不填写未经推导和审查的“安全最大文件大小”。

首版不提供追加、原位数据修改或断点续写。内容变更、重新压缩、取消后重新开始，均生成新 DEK、新容器身份和新 salt；禁止沿用旧密钥与记录序号加密不同字节。只读重试与新加密调用必须在接口中分清。

## 7. 压缩、元数据与资源边界

小文件按完整文件合包，暂以 4 MiB（4 × 1024 × 1024 字节）逻辑文件数据为目标；包未达目标时加入下一个小文件，达到或超过目标便封包，因此允许跨过目标，不为凑齐目标拆开该小文件。按暂定的小文件界限严格小于 4 MiB，单包逻辑文件数据严格小于 8 MiB；映射、记录编码与压缩后的尺寸另有硬限制，不能把 4 MiB 目标直接当作读取缓冲的最大值。空文件只记入清单，不生成数据片段；清单条目数、包内条目数和映射大小均须独立限制。

启用压缩时，每个包或大文件块的数据区先独立尝试压缩，再加密；压缩后没有变小则保存未压缩编码。默认关闭压缩、现有开关及等级 3 保持 v1 使用策略。压缩记录的数据区恰好包含一个完整 Zstd 帧，不接受外部字典、拼接帧、可跳过帧或帧后尾字节；这是容器限定的接受范围，不代表这些形式在 Zstd 标准中均非法。清单与映射信息不压缩。

记录的压缩或未压缩编码标志与相关长度均须认证；读取时先完整认证该记录，再按其编码解压或直接校验受限数据。必须限制压缩帧窗口、单包输出、累计输出、记录数、包内条目数和清单规模。已通过 AEAD 的压缩流仍可能非法或耗尽资源，认证不能替代格式检查。性能和容量评估暂缓，不取消这些解析边界或每密钥使用预算。

名称、单文件或目录类型、目录关系及文件大小放入加密清单。公共字段仅保留版本路由、解锁和有界解析所需信息。未解锁的 `info` 必须说明公共信息未认证，不能把未验证的字段当作可信状态。

加密清单不隐藏容器总大小、记录数量、记录尺寸和访问时间；不承诺抵御流量分析。数据认证也不能证明容器是最新版本，完整旧文件被替换回来仍可合法通过认证。[RFC 5116 的适用范围](https://www.rfc-editor.org/rfc/rfc5116.html#section-1.2)

## 8. rekey 的首版语义

`rekey` 与 `-r` 等价，依次读取旧密码、新密码及确认输入。v2 换密生成新 DEK、新容器身份、新 salt 及相应 nonce，完整重新加密；源文件必须全部认证并完成内容检查，新输出完成验证后才通过事务发布。过程中不主动生成完整解密载荷临时文件。

默认保留源文件，只有显式 `--replace` 才替换源路径。普通输出拒绝既有目标及与输入相同的目标；替换沿用平台事务和失败清理语义。首版保持源格式版本：v1 交给 v1 换密流程，v2 交给 v2，不隐式迁移。

只重包相同 DEK 不属于首版 `rekey`。旧密码加上保存的旧包装头可以恢复未轮换的 DEK，即使没有保留旧载荷，也可能解开继续使用该 DEK 的当前数据。未来若提供只重包，必须独立说明这一限制，以及完整验证和事务复制仍可能需要全量 IO。

完整轮换也不会让保留下来的旧文件、历史备份或已恢复明文失效。首版保留源文件的数据算法、压缩模式和 KDF 参数，同时更新密码及上述随机材料；KDF 参数升级留待后续显式选项，不隐式升级，也不顺带迁移文件格式。

## 9. RSA 与其他能力的取舍

首版不增加 RSA、公钥收件人、签名、多密码入口或恢复密钥。它们各自有不同的使用场景，不能通过增加一个“算法”选项一并解决。

| 能力 | 值得立项的场景 | 需要另外解决的问题 |
| --- | --- | --- |
| 公钥收件人 | 给他人发送文件，或备份机器只持公钥而恢复私钥离线保管 | 密钥生成、导入、身份核对、私钥保护及丢失恢复 |
| RSA 支持 | 需要兼容现有 RSA 密钥、证书或硬件 | OAEP 套件、参数、密钥格式及依赖能力；不直接用 RSA 加密文件载荷 |
| 签名 | 需要证明作者身份或发布来源 | 独立签名密钥、可信公钥来源、签名覆盖范围与验证策略 |
| 独立恢复密钥 | 用户预先保存恢复材料，应对忘记密码 | 新增解锁入口、展示保存流程及恢复材料泄露的后果 |

公钥收件人仍保护随机数据密钥，数据继续使用对称 AEAD。没有旧密钥兼容需求时，后续优先评估基于 X25519 的标准化混合方案，例如 HPKE；最终选择需要与 Botan 支持范围、密钥格式和威胁模型共同核对。[RFC 9180 概述](https://www.rfc-editor.org/rfc/rfc9180.html#section-1)

公钥加密不自动证明发送者身份，多个解锁入口不等于多因素验证，也不提供读写权限隔离。删除入口不能撤销已获知的 DEK；要阻止旧密钥读取重新生成的当前数据，仍需轮换数据密钥并重加密。上述能力不会仅因存在版本字段就自动获得安全的扩展方式。

## 10. 冻结前的验收要求

- 给出两套完整套件的编号、原语、参数、域标签、nonce、认证范围及使用预算；文档中的概念图不能代替这些定义。
- 给出固定密码字节、salt、DEK、容器身份、派生结果、AAD、逐记录密文与 END 的确定性向量；固定随机值只用于测试。
- 覆盖空载荷、多块、小文件合包及跨目标封包、压缩回退与混合编码、加密清单、Unicode 密码及空白字节，确保跨平台结果一致。
- 覆盖头替换、包装替换、记录删改和错序、跨容器拼接、END 缺失、尾部追加、边界溢出及有效认证但非法内容。
- 检查提交前失败、取消和磁盘故障不发布最终输出；提交后持久化确认失败应准确说明文件已提交，不承诺回滚。密码与密钥不进入诊断信息，重新开始不复用旧密钥和 nonce。
- 由独立审查核对组合安全与资源预算，并完成 v1 历史文件回归后，才能宣称实现满足本规范。

这些条目是后续设计与实现的验收条件，目前不表示向量已经生成、测试已经通过或协议已经冻结。
